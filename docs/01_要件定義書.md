## 1. システム概要

### 1.1 システム名（仮）
落ちものパズルゲーム（テトリス風Webアプリケーション）

### 1.2 概要
プレイヤーがブラウザ上でブロック（テトリミノ）を操作し、列を揃えて消していく落ちものパズルゲーム。単体でも遊べる完結したゲームとしつつ、ユーザー登録・スコア登録・ランキング表示など、フロントエンドとバックエンドの双方に一定の実装ボリュームを持たせる機能構成とする。

### 1.3 想定利用シーン
- 利用者がブラウザからアクセスし、個人でプレイする
- プレイ後にニックネームでスコアを登録し、ランキングを確認できる
- 自分自身の過去のプレイ結果（履歴）を確認できる

## 2. 前提条件・決定事項

| 項目 | 決定事項 |
|---|---|
| ゲーム内容 | テトリス風・落ちものパズル |
| バックエンド言語／フレームワーク | Python 3.11以上 / FastAPI |
| データ永続化 | SQLite（SQLAlchemy ORM経由） |
| フロントエンド | HTML / CSS / JavaScript（Vanilla JS。ビルドツール・フレームワークは使用しない） |
| API形式 | REST API（JSON）。FastAPIの自動生成するSwagger UI（`/docs`）をAPI仕様確認・動作確認に活用する |
| Gitリポジトリ | https://github.com/alpacamasyu 配下に新規リポジトリを作成（詳細は「8. リポジトリについて」） |
| ホールド機能 | 基本実装には含めない（発展課題扱い） |
| ゴースト表示（落下予測位置） | 基本実装に含める（衝突判定・座標計算の理解に資するため） |

> **バックエンド実装ボリュームに関する補足**
> 落ちものパズルはゲームロジック（落下・回転・衝突判定・ライン消去）の多くがフロントエンド（JavaScript）側の処理になりやすい特性がある。フロントエンドとバックエンド双方の実装経験を確保するため、以下をバックエンドの責務として明確に切り出す。
> - テトリミノの出現順序生成（7-bagアルゴリズム）をAPIで提供し、フロントエンドはそれを取得して使用する
> - ユーザー登録・簡易ログイン
> - スコア登録・ランキング取得
> - プレイ履歴の保存・参照
> - 難易度（レベル）ごとの落下速度など、ゲーム設定のマスタデータ管理
>
> この切り分けにより「フロントエンド＝画面・操作・描画」「バックエンド＝データ管理・ゲームルールの一部・API提供」という役割分担を明確化する。

## 3. 機能要件

### 3.1 機能一覧

| ID | 機能名 | 概要 | 主担当 |
|---|---|---|---|
| F-01 | ユーザー登録・ログイン | ニックネーム等の簡易情報でユーザーを識別する（本格的な認証基盤は範囲外） | バックエンド |
| F-02 | ゲームプレイ画面 | ゲーム盤面の描画、操作UI、スコア・レベル表示 | フロントエンド |
| F-03 | テトリミノ操作 | 左右移動・回転・ソフトドロップ・ハードドロップ | フロントエンド |
| F-04 | テトリミノ出現順序の取得 | 7-bagアルゴリズムによる出現順序をバックエンドAPIから取得 | バックエンド／フロントエンド連携 |
| F-05 | ライン消去・得点計算 | 揃った行の削除、得点加算、複数ライン同時消去のボーナス | フロントエンド |
| F-06 | レベル・落下速度制御 | 消去ライン数に応じたレベルアップと落下速度の変化 | フロントエンド／バックエンド（設定値提供） |
| F-07 | ゲームオーバー判定 | 積み上がりによるゲーム終了判定、結果表示 | フロントエンド |
| F-08 | スコア登録 | ゲーム終了時のスコアをバックエンドへ送信・保存 | バックエンド |
| F-09 | ランキング表示 | 上位スコア（例：TOP10）を取得・表示 | バックエンド／フロントエンド |
| F-10 | プレイ履歴参照 | 自分の過去のプレイ結果一覧を取得・表示 | バックエンド／フロントエンド |
| F-11 | 難易度・ゲーム設定管理 | 難易度ごとの初期落下速度などのマスタデータをバックエンドで管理 | バックエンド |

### 3.2 各機能の詳細

**F-01 ユーザー登録・ログイン**
簡易実装とし、パスワード等を用いた本格的な認証は行わない。ニックネーム（一意な文字列）を入力してユーザーを識別し、以降のスコア登録・履歴参照と紐づける。

**F-02〜F-03 ゲームプレイ画面／操作**
標準的な落ちものパズルの操作感（キーボード操作：左右移動、回転、ソフトドロップ、ハードドロップ）を実装する。画面はゲーム盤面、次のミノ表示（ネクスト）、ゴースト表示（落下予測位置）、スコア・レベル・ライン消去数を表示する。ホールド機能は基本実装には含めず、発展課題とする。

**F-04 テトリミノ出現順序の取得**
ゲーム開始時、およびミノを使い切るタイミングで、バックエンドAPIから次に出現するミノの並び（7種類のミノをランダムな順で1巡させる7-bag方式）を取得する。

**F-05〜F-07 ゲーム進行ロジック**
一般的な落ちものパズルのルールに準拠する。詳細な採点ルール（1ライン消去・2ライン同時消去・テトリス〈4ライン同時〉のボーナス等）は基本設計・詳細設計で確定する。

**F-08〜F-10 スコア・ランキング・履歴**
ゲーム終了時にニックネーム・スコア・到達レベル・プレイ日時をバックエンドへ送信し、SQLiteに保存する。ランキング画面では上位スコアを一覧表示し、履歴画面では自分自身の過去のプレイ結果を確認できる。

**F-11 難易度・ゲーム設定管理**
易しい／普通／難しい等の難易度区分ごとに初期落下速度や得点倍率などをバックエンド側でマスタデータとして保持し、APIで提供する。フロントエンドはこの値を用いてゲームパラメータを初期化する。

### 3.3 スコープ外（本システムでは扱わない機能）
- 本格的なユーザー認証（パスワード・OAuth等）
- リアルタイム対戦・マルチプレイヤー機能
- スマートフォン等でのタッチ操作最適化（PCブラウザでの操作を基本とする）
- 本番環境への公開・デプロイ運用（ローカル環境での動作を基本とする）

## 4. 非機能要件

| 分類 | 要件 |
|---|---|
| 動作環境（フロントエンド） | 最新版のGoogle Chromeで動作すること |
| 動作環境（バックエンド） | Python 3.11以上で動作すること |
| パフォーマンス | API応答時間は通常時1秒以内を目安とする |
| セキュリティ | SQLインジェクション対策（ORM・パラメータバインドの使用）、入力値バリデーションを実施する。本格的な認証・認可基盤の構築は範囲外とする |
| コーディング規約 | PEP8に準拠する。型ヒントを積極的に使用する（FastAPI／Pydanticとの親和性のため） |
| テスト | 主要なAPI・ロジックに対し、pytestによる単体テストを作成する |
| ドキュメント | リポジトリにREADMEを整備し、セットアップ手順・起動手順を明記する |
| 保守性 | コードにはコメント・docstringを付与し、可読性を保つ |

## 5. システム構成

```
[ブラウザ]
   │  HTML/CSS/JavaScript（画面表示・ユーザー操作）
   │  fetch API による REST 通信（JSON）
   ▼
[FastAPIアプリケーション]（Python 3.11+）
   │  SQLAlchemy ORM
   ▼
[SQLite データベース]
```

- フロントエンドとバックエンドは、別々のブランチ・作業単位として開発を進める
- 通信はREST API（JSON形式）とし、FastAPIが自動生成するSwagger UI（`/docs`）でAPI仕様を確認しながら開発する

## 8. 用語集

| 用語 | 説明 |
|---|---|
| テトリミノ | 落ちものパズルで使用される、4つの正方形からなるブロック（I, O, T, S, Z, J, L の7種類） |
| 7-bagアルゴリズム | 7種類のテトリミノを1セットとしてランダムな順で出現させ、偏りを防ぐ方式 |
| REST API | HTTPを用いて、リソースに対するCRUD操作をURLとHTTPメソッドの組み合わせで表現するAPI設計方式 |
| ORM | Object-Relational Mapping。Pythonのオブジェクトとデータベースのレコードを対応付ける仕組み（本システムではSQLAlchemyを使用） |
