## 1. システムアーキテクチャ

### 1.1 全体構成

```
[ブラウザ]
   │ HTML/CSS/JavaScript（画面表示・ユーザー操作）
   │ fetch API による REST 通信（JSON）
   ▼
[FastAPIアプリケーション]（Python 3.11+）
   ├─ routers   … エンドポイント定義（リクエスト受付・レスポンス返却）
   ├─ schemas   … Pydanticモデル（リクエスト／レスポンスの型定義・検証）
   ├─ crud      … DB操作（登録・取得・更新処理）
   └─ models    … SQLAlchemyモデル（テーブル定義）
   ▼
[SQLite データベース]
```

### 1.2 層ごとの責務

| 層 | 責務 |
|---|---|
| routers | HTTPリクエストの受付、パラメータのバリデーション呼び出し、crud層の呼び出し、レスポンス返却 |
| schemas | APIのリクエスト・レスポンスの型定義（Pydantic）。バリデーションルールを含む |
| crud | データベースへの読み書き処理（SQLAlchemyセッションを用いたCRUD操作） |
| models | テーブル構造の定義（SQLAlchemyモデル） |

初学者向けの研修であることを踏まえ、サービス層などの抽象化は設けず、上記4層のシンプルな構成とする。

## 2. 画面設計

### 2.1 画面一覧

| No | 画面名 | 概要 |
|---|---|---|
| S-01 | ログイン画面 | ニックネームを入力し、ユーザー登録／ログインを行う |
| S-02 | メニュー画面 | ゲーム開始、難易度選択、ランキング、履歴への導線を表示する |
| S-03 | ゲームプレイ画面 | テトリミノを操作してプレイする画面。盤面・ネクスト・ゴースト・スコア・レベルを表示する |
| S-04 | リザルト画面 | ゲームオーバー時にスコア・到達レベルを表示し、スコアを登録する |
| S-05 | ランキング画面 | 上位スコア（TOP10）の一覧を表示する |
| S-06 | 履歴画面 | ログイン中ユーザーの過去のプレイ結果一覧を表示する |

### 2.2 画面遷移

```
S-01 ログイン
  │ ログイン成功
  ▼
S-02 メニュー ─┬─ 難易度選択 → ゲーム開始 → S-03 ゲームプレイ
              │                              │ ゲームオーバー
              │                              ▼
              │                          S-04 リザルト ── スコア登録 ── メニューへ戻る
              ├─ ランキングを見る → S-05 ランキング → メニューへ戻る
              └─ 履歴を見る     → S-06 履歴     → メニューへ戻る
```

各画面の詳細なレイアウト・表示項目・操作仕様は詳細設計書で定める。

## 3. API設計（概要）

### 3.1 API一覧

| No | Method | エンドポイント | 概要 | 対応機能ID |
|---|---|---|---|---|
| A-01 | POST | /api/users | ユーザー登録（ニックネーム） | F-01 |
| A-02 | POST | /api/login | ログイン（既存ユーザーの確認） | F-01 |
| A-03 | GET | /api/tetromino-sequence | 7-bag方式によるテトリミノ出現順序の取得 | F-04 |
| A-04 | GET | /api/difficulty-settings | 難易度別のゲーム設定（初期落下速度・得点倍率等）の取得 | F-11 |
| A-05 | POST | /api/scores | スコア登録（ニックネーム・スコア・到達レベル・難易度） | F-08 |
| A-06 | GET | /api/rankings | ランキング取得（上位N件、既定値10件） | F-09 |
| A-07 | GET | /api/users/{user_id}/history | 指定ユーザーのプレイ履歴取得 | F-10 |

各APIの詳細なリクエスト・レスポンス形式、ステータスコード、エラー仕様は詳細設計書で定める。API仕様はFastAPI起動時に自動生成されるSwagger UI（`/docs`）でも確認できるようにする。

### 3.2 API設計方針
- REST原則に沿ったエンドポイント設計とする（リソース名は複数形、HTTPメソッドで操作を表現）
- リクエスト・レスポンスはすべてJSON形式とする
- 入力値のバリデーションはPydanticスキーマで行う
- エラー時は適切なHTTPステータスコード（400系／404／500等）とエラーメッセージを返却する

## 4. データベース設計（概要）

### 4.1 テーブル一覧

| テーブル名 | 概要 |
|---|---|
| users | ユーザー情報（ニックネーム等） |
| scores | プレイごとのスコア記録 |
| difficulty_settings | 難易度別のゲーム設定マスタ |

### 4.2 ER概要

```
users (1) ──< (N) scores
difficulty_settings (1) ──< (N) scores   ※ difficulty列で対応づけ
```

### 4.3 テーブル概要

**users**
ニックネーム（一意）を主キーに準じる項目として保持し、ユーザーを識別する。

**scores**
どのユーザーが、どの難易度で、いつ、どのくらいのスコア・到達レベルを記録したかを保持する。ユーザーへの外部キーを持つ。

**difficulty_settings**
難易度区分（易しい／普通／難しい）ごとに、初期落下速度・得点倍率などのパラメータを保持するマスタテーブル。初期データとして研修開始前に3件程度を投入しておく。

詳細なカラム定義（型・制約・初期データ）は詳細設計書で定める。

## 5. ゲームロジックの責務分担（設計方針）

| 処理 | 担当 | 補足 |
|---|---|---|
| テトリミノの落下・移動・回転・衝突判定 | フロントエンド | Canvas上でリアルタイムに処理する |
| テトリミノの出現順序 | バックエンド（生成）／フロントエンド（消費） | A-03で取得した順序をフロントエンドの内部キューで管理する |
| ライン消去判定・得点計算 | フロントエンド | 得点倍率のみバックエンドの難易度設定値（A-04）を参照する |
| ゲームオーバー判定 | フロントエンド | 判定後、A-05でスコアを登録する |
| スコアの永続化・ランキング集計 | バックエンド | フロントエンドは表示のみを担当する |

## 6. リポジトリ・ブランチ構成

### 6.1 リポジトリ
- https://github.com/alpacamasyu/python-tetris-training （要件定義書 7章のとおり）

### 6.2 ブランチ構成

| ブランチ名 | 用途 | 保護設定 |
|---|---|---|
| `main` | 完成品（模範解答）。研修開始前に実装を完了させ、研修中は保護ブランチとして直接変更不可とする | 保護（直接push禁止、研修生からの変更不可） |
| `backend` | バックエンド実装用。研修生はこのブランチを起点に作業する | 保護なし（研修生が直接コミット、または機能単位でPRを作成） |
| `frontend` | フロントエンド実装用。研修生はこのブランチを起点に作業する | 保護なし（同上） |
| `integration` | Day5に`backend`と`frontend`をマージし、結合確認を行うためのブランチ | 保護なし |

### 6.3 初期状態（研修開始前に準備しておくもの）
- `main`：完成品一式（バックエンド・フロントエンドともに実装済み）
- `backend`：バックエンドのディレクトリ構成・雛形（環境設定ファイル、空のmain.py等）のみを配置し、実装本体は研修生が行う
- `frontend`：フロントエンドのディレクトリ構成・雛形（index.html、CSS雛形等）のみを配置し、実装本体は研修生が行う

### 6.4 コミット・PR運用（簡易ルール）
- コミットメッセージは `feat: スコア登録APIを実装` のように、種別（feat/fix/docs/test等）を先頭に付与する
- 機能単位でコミットを分け、こまめにコミットする
- Day5には`backend`→`integration`、`frontend`→`integration`へそれぞれプルリクエストを作成し、結合確認を行う（レビュー・マージの体験を兼ねる）
